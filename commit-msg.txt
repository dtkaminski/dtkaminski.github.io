Count the arrival, not just the navigation

page_view had two call sites and both were inside navigation handlers — window.__oiGo
and the go={} prop. Nothing fired on arrival. A session that signed in, landed on
Today and stayed there wrote no events at all: no denominator for
time_to_first_action, and vw_product_activation.sessions undercounting by every
visitor who never changed page.

Found the hard way. Dan signed in at 11:25, the dashboard loaded clean — brand_users,
user_brand_ids, vw_brand_action_board, cache_brand_today all 200, 206 requests in
twenty minutes — and product_events was still empty three minutes later. I had read
that emptiness as "nobody has used the app yet" for most of the day. It was my own
instrumentation gap.

So the V3 shell now fires one page_view on first mount with the landing destination,
tagged arrival:true so an arrival is separable from a navigation in analysis.

Guarded on window.__oiArrivalSeen rather than a module-level flag: greta-app.js is a
classic top-level script sharing one global scope with the embeds, and a new
top-level binding there is exactly how cost-entry.build.js took the whole app down on
29 Sep. Once per tab is the right grain — the tracker's session id is per-tab too, so
a remount is the same visit and must not read as a second arrival, while navigating
away and back is a real page_view and still fires through __oiGo.

The event lands before brand_id resolves, which is what greta-track.js's pending
queue was built for: it holds and flushes on frkl-brand-ready. That path is already
proven — an earlier visit this morning fired five tracker POSTs, which PostgREST
rejected with 404 only because its schema cache did not yet have the table. It does
now; the 401s that followed prove the relation resolves.

Verified: node --check passes, the hook sits between two existing effects rather than
below a conditional return, and the compiled form is the guarded single-fire.
